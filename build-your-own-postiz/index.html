How to Vibe Code Your Own Postiz Alternative

One post, every network, no tab circus. Postiz charges $29–$99 per month — that’s $348–$1188 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 10 hoursCross-posting is a loop

Who this replacement is for

This build targets one creator or small brand posting the same content to several networks. The goal: write once, tailor the copy per network, and publish everywhere on schedule. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

Same build, different logo: this v1 also replaces FeedHive, Post Bridge and SocialBee — they all solve the same core job.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of Postiz you actually use.

EstimateWhat you get
10 hourstwo networks, queue, scheduled publishing
3 daysper-network variants, previews, retries, calendar
1 month+every network api, token zoo, teams, analytics — the part you should probably skip

What a minimal Postiz alternative needs

  • connected channels for the networks you actually use
  • compose once with per-network variant editing and live previews
  • character limits, image specs, and link handling per network
  • a shared queue and calendar across all channels
  • per-channel publishing status with retries and a readable log

Data model

Channel, Post, PostVariant, MediaAsset, PublishAttempt

Integrations

two social network APIs first, Cloudflare Cron Triggers

Capability context

Astro, Workers, R2

The guardrail

Encrypt provider tokens, make each channel’s publish attempt idempotent, and never let one network’s failure block the others.

Deliberate non-goals

Do not build AI caption writing, analytics dashboards, approval workflows, or every network on day one.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Fanout”, a deliberately focused alternative to Postiz. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: one creator or small brand posting the same content to several networks.
Primary outcome: write once, tailor the copy per network, and publish everywhere on schedule.
Product principle: optimize the exact workflow below instead of copying the full breadth of Postiz. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The owner connects two channels through OAuth, composes a post with an image, tweaks the variant for each network, and schedules it for tomorrow morning.
2. The scheduler publishes to both channels; one succeeds and one fails, the owner reads the error in the log, fixes the variant, and retries only the failed channel.
3. The owner reviews the weekly calendar, drags a queued post to a new slot, and sees every channel’s publishing status roll up on the dashboard.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Compose: shared draft, per-network variant tabs with live previews, character counters, media attachments, and schedule controls.
2. Calendar: a weekly grid of queued and published posts across channels, drag-to-reschedule, and per-channel status badges.
3. Channels: connected accounts with token health, reconnect actions, per-channel posting defaults, and a pause toggle.
4. Publishing log: attempts with timestamp, channel, response summary, retry action, and filters for failed and pending.

CORE CAPABILITIES
1. connected channels for the networks you actually use
2. compose once with per-network variant editing and live previews
3. character limits, image specs, and link handling per network
4. a shared queue and calendar across all channels
5. per-channel publishing status with retries and a readable log

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Store one canonical post with per-channel variants; publishing uses the variant and falls back to the canonical text only when no variant exists.
2. Encrypt provider tokens at rest, refresh them ahead of expiry, and mark a channel unhealthy instead of failing silently when refresh fails.
3. Make each channel’s publish attempt idempotent with a deduplication key so retries never double-post.
4. Publish channels independently: one network’s outage or rejection never blocks or rolls back the others.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Channel, Post, PostVariant, MediaAsset, PublishAttempt. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Astro, Workers, R2 as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with two social network APIs first and Cloudflare Cron Triggers. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Encrypt provider tokens, make each channel’s publish attempt idempotent, and never let one network’s failure block the others.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. Given a post scheduled to two channels while one API is down, the healthy channel publishes on time and the failed attempt is logged with a retry available.
2. Given a retry of a failed attempt after a transient error, the post appears exactly once on that network.
3. Given an expired channel token, the queue pauses for that channel, the owner sees a reconnect prompt, and queued posts resume after reconnection.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not build AI caption writing, analytics dashboards, approval workflows, or every network on day one.

Product principle: optimize the exact workflow below instead of copying the full breadth of Postiz. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The owner connects two channels through OAuth, composes a post with an image, tweaks the variant for each network, and schedules it for tomorrow morning.
2. The scheduler publishes to both channels; one succeeds and one fails, the owner reads the error in the log, fixes the variant, and retries only the failed channel.
3. The owner reviews the weekly calendar, drags a queued post to a new slot, and sees every channel’s publishing status roll up on the dashboard.

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Store one canonical post with per-channel variants; publishing uses the variant and falls back to the canonical text only when no variant exists.
2. Encrypt provider tokens at rest, refresh them ahead of expiry, and mark a channel unhealthy instead of failing silently when refresh fails.
3. Make each channel’s publish attempt idempotent with a deduplication key so retries never double-post.
4. Publish channels independently: one network’s outage or rejection never blocks or rolls back the others.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Channel, Post, PostVariant, MediaAsset, PublishAttempt. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

Build just one piece

Not ready to replace all of Postiz? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

Publish to five networks, fail on one, roll back noneCross-posting is a fan-out of independent attempts, not a transaction.
Build the publishing engine for a cross-posting tool: one scheduled post fans out to several connected networks, and each channel lives or dies alone.

Model every channel's publish as an independent attempt with its own status, response log, and retry budget; there is no all-or-nothing transaction, and one network's outage must never block or roll back the others. Make each attempt idempotent with a deduplication key derived from post and channel, checked before any API call, so a crashed worker restarting or an impatient retry never double-posts, the one sin your users will screenshot. Distinguish failure types: transient errors (timeouts, rate limits) retry automatically with backoff; permanent rejections (variant too long, image spec violation) stop and surface the network's actual error message for a human. Retrying from the log re-fires only the failed channel. Roll statuses up so the post shows per-channel badges: published, retrying, failed, with timestamps.

Done when: one network being down leaves the others published on schedule, a retried transient failure results in exactly one live post on that network, and a permanent rejection shows the real reason instead of retrying forever.
The token babysitterOAuth tokens expire at 3 AM. Your queue shouldn’t die with them.
Build OAuth token lifecycle management for a social posting tool that holds credentials for several networks.

Encrypt every access and refresh token at rest with a key kept outside the database, so a leaked backup leaks no accounts. Track each token's expiry and refresh proactively ahead of it, on a schedule, not reactively at publish time, because publish time is exactly when you can least afford a refresh round-trip failing. Serialize refreshes per channel with a lock: two workers refreshing the same token concurrently can invalidate each other on providers with rotating refresh tokens, and always persist the new refresh token atomically with the new access token. When refresh fails for real (revoked access, changed password), do not fail silently and do not hammer the provider: mark the channel unhealthy, pause its queued posts in a held state, and surface a reconnect prompt. After the owner reauthorizes, held posts resume, with a confirmation for anything now embarrassingly stale.

Done when: tokens are unreadable in a database dump, an expired-token channel pauses with a visible reconnect prompt instead of a silent failure streak, and reconnection resumes the queue without double-posting.
Character counting that knows each network’s rulesThe same draft is 240 characters on one network and 302 on another.
Build per-network length validation for a cross-posting composer, where one canonical draft plus optional per-network variants must each fit their destination's rules.

Encode each network's counting quirks as a pluggable profile: one network counts every URL as a fixed 23 characters regardless of length, others count real length; some count certain Unicode ranges as two characters; grapheme clusters, emoji with modifiers, family emoji, must count as the network counts them, not as your language's naive string length reports. Run the right counter against the effective text per channel, which is the variant when one exists and the canonical text otherwise, and show a live counter per network tab that turns red past the limit. Validate at three moments: while typing, at scheduling, and again at publish time, since an edit to the canonical text can silently push a variant-less channel over its limit days after scheduling.

Done when: a draft with two links and a string of emoji shows correct, different counts per network, editing the canonical text re-validates every channel without a variant, and nothing over-limit ever reaches a network API.
Drag a post to ThursdayA calendar queue where rescheduling is a drag, in the good way.
Build the drag-to-reschedule calendar for a social posting queue: a weekly grid showing queued and published posts across channels, where dragging a queued post to a new slot reschedules it.

Render posts as cards in day-and-time slots, with per-channel status badges. Implement the drag with proper affordances: a ghost card following the cursor, target slots highlighting, and an immediate optimistic move that rolls back visibly if the server rejects it. Enforce the rules at drop time: published and currently-publishing posts are immovable, dragging into the past bounces with a message, and a post mid-drag when its publish moment arrives must resolve sanely, publish wins, the drag cancels. Store times in UTC but render the grid in the owner's display timezone, and treat a drop as picking a wall-clock time in that zone. Guard against a stale-grid race with a version check so dragging based on old data cannot clobber a concurrent edit from another tab.

Done when: dragging a queued post updates its publish time correctly across a timezone boundary, a published post refuses to budge, and a rejected drop animates the card back with the reason shown.

Frequently asked questions

How long does it take to build your own Postiz?

A basic version — two networks, queue, scheduled publishing — takes about 10 hours. Roughly 3 days gets you a solid v1 with per-network variants, previews, retries, calendar. Matching everything Postiz really does (every network api, token zoo, teams, analytics) is closer to 1 month+, which is exactly why you should scope down instead.

How much does Postiz cost if I keep subscribing?

Postiz runs $29–$99 per month on public paid plans, which is $348–$1188 per year. A focused self-built replacement costs your build time plus close-to-zero hosting.

What stack should I use to build a Postiz alternative?

The build prompt on this page ships in four flavors: the AHA stack (Astro, HTMX, Alpine.js), Next.js, Laravel, and Ruby on Rails. The capability context for this product is Astro, Workers, R2. Pick the stack you already know — the scope matters more than the framework.

What features does a minimal Postiz replacement need?

A useful v1 needs: connected channels for the networks you actually use; compose once with per-network variant editing and live previews; character limits, image specs, and link handling per network; a shared queue and calendar across all channels; per-channel publishing status with retries and a readable log. Everything else is scope creep until you personally miss it.

What should I deliberately not build?

Do not build AI caption writing, analytics dashboards, approval workflows, or every network on day one.

Does this build also replace FeedHive, Post Bridge and SocialBee?

Yes. Postiz, FeedHive, Post Bridge and SocialBee all solve the same core job — write once, tailor the copy per network, and publish everywhere on schedule. The scoped v1 on this page covers what most people use any of them for, so one focused build replaces whichever you currently pay for.
