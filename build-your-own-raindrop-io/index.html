How to Vibe Code Your Own Raindrop.io Alternative

Every link you swore you’d revisit, findable this time. Raindrop.io charges $2.33–$3 per month — that’s $28–$36 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 3 hoursSatisfyingly simple

Who this replacement is for

This build targets one person hoarding links across every device. The goal: save links with tags and collections in one place and actually find them again. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

Same build, different logo: this v1 also replaces Pinboard and GoodLinks — they all solve the same core job.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of Raindrop.io you actually use.

EstimateWhat you get
3 hourssave links, tags, search
1 daybookmarklet, collections, duplicate detection, excerpts
1 month+browser extensions, mobile apps, full-page archiving — the part you should probably skip

What a minimal Raindrop.io alternative needs

  • one-click saving via a bookmarklet with autofilled title and description
  • tags, collections, and favorites
  • full-text search across titles, descriptions, and stored excerpts
  • card and list views with domain favicons
  • duplicate detection by normalized URL

Data model

Bookmark, Collection, Tag

Integrations

bookmarklet, page metadata extraction

Capability context

Astro, HTMX, D1

The guardrail

Fetch metadata server-side with timeouts and size caps, and store only the excerpt needed for search.

Deliberate non-goals

Do not build team sharing, public collections, AI summaries, or a full read-later reading experience.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Pincushion”, a deliberately focused alternative to Raindrop.io. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: one person hoarding links across every device.
Primary outcome: save links with tags and collections in one place and actually find them again.
Product principle: optimize the exact workflow below instead of copying the full breadth of Raindrop.io. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The owner drags the bookmarklet to the toolbar, saves a page from any site, and sees the title, description, and favicon filled in automatically.
2. The owner tags a batch of saved links, moves them into a collection, and browses the collection in card view.
3. The owner searches a half-remembered phrase, finds the bookmark through its stored excerpt, opens it, and marks it a favorite.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Library: card and list toggle, collection sidebar, tag filters, favorites, sort controls, and quick edit and delete actions.
2. Save view: URL field, autofilled title, description, and excerpt, tag picker, collection selector, and duplicate warning.
3. Search: single query box, matches highlighted in titles and excerpts, tag and collection filters, and an empty-state with tips.
4. Bookmarklet setup: draggable bookmarklet, a copy-paste fallback, and a test-save flow that confirms everything works.

CORE CAPABILITIES
1. one-click saving via a bookmarklet with autofilled title and description
2. tags, collections, and favorites
3. full-text search across titles, descriptions, and stored excerpts
4. card and list views with domain favicons
5. duplicate detection by normalized URL

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Normalize URLs before saving and detect duplicates by normalized URL, offering to update the existing bookmark instead.
2. Fetch page metadata server-side with a timeout, a size cap, and no execution of remote scripts.
3. Store only the text excerpt needed for search and index it so search stays fast as the library grows.
4. Authenticate every save, including bookmarklet requests, with a token the owner can rotate.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Bookmark, Collection, Tag. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Astro, HTMX, D1 as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with bookmarklet and page metadata extraction. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Fetch metadata server-side with timeouts and size caps, and store only the excerpt needed for search.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. Given a page that blocks metadata fetching, the bookmark still saves with the URL and a manually editable title.
2. Given the same URL saved twice, the library keeps one bookmark and merges the newer tags into it.
3. Given a search for a phrase that appears only in a stored excerpt, the matching bookmark is returned with the phrase highlighted.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not build team sharing, public collections, AI summaries, or a full read-later reading experience.

Build just one piece

Not ready to replace all of Raindrop.io? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

The same link, saved twice, stored onceURL normalization and duplicate detection that knows utm_source is noise.
Build duplicate detection for a bookmarking tool, built on URL normalization.

Normalize before every save: lowercase the scheme and host, strip default ports, resolve trailing-slash variance, drop fragments, sort remaining query parameters, and remove known tracking parameters, utm_*, fbclid, gclid, ref, so the same article arriving from a newsletter and from Twitter normalizes identically. Keep meaningful query strings intact: a video id or search query changes the page and must survive. Store both the original URL for opening and the normalized form, uniquely indexed, for matching.

On a duplicate hit, don't reject and don't silently drop: offer to update the existing bookmark, and when accepted, merge the newer tags into it, keep the earlier saved date, and refresh title and description if the new fetch got better metadata.

Done when: the same article with different UTM junk matches as one bookmark, two YouTube URLs differing by video id stay separate, and a duplicate save merges tags without losing the original save date.
Fetching strangers’ pages without getting hurtTimeouts, size caps, SSRF checks, and a graceful save when the site blocks you.
Build the server-side metadata fetcher for a bookmarking tool: given a URL, return title, description, and favicon for autofill.

Fetch defensively. Enforce a hard timeout of a few seconds, cap the downloaded bytes and read streaming so a 2GB page dies early, follow a bounded number of redirects, and parse HTML with a real parser, never executing scripts or loading subresources. Block server-side request forgery: resolve the hostname first and refuse private, loopback, and link-local ranges, re-checking after each redirect, so a bookmark for an internal IP can't probe your network. Extract title, open-graph fields, and meta description, decode character sets properly, and grab the favicon with the same caps.

Failure must not block saving: when a site times out, blocks bots, or returns garbage, save the bookmark with the bare URL and an editable empty title, flagged for manual naming.

Done when: a URL pointing at an internal address is refused before any connection, a huge or hanging page fails within the caps, and a fetch-hostile page still saves as a usable, editable bookmark.
Find it by the phrase you half-rememberFull-text search across titles and stored excerpts, with the match highlighted.
Build search for a personal bookmark library: one query box over titles, descriptions, and stored page excerpts.

Use a real full-text index, SQLite FTS5 or your database's equivalent, not LIKE queries that collapse at a few thousand rows. Index title, description, and the excerpt captured at save time, weighting title matches above excerpt matches in ranking. Support multi-word queries as AND by default, with prefix matching on the final term so results appear while typing.

Return snippets: for each hit, extract the region of the excerpt around the match and highlight the matched terms, safely escaped, since excerpts are text from arbitrary websites. Combine search with the structural filters, tag, collection, favorites, as index-friendly conjunctions rather than post-filtering in application code. Keep the index in sync transactionally when bookmarks are added, edited, or deleted.

Done when: a phrase appearing only in a stored excerpt finds its bookmark with the phrase highlighted, typing progressively narrows results without full-word completion, and a deleted bookmark disappears from results immediately.
The bookmarklet is an API client you can’t updateOne-click saving from any page, authenticated by a token the owner can rotate.
Build the bookmarklet save flow for a bookmarking tool.

The bookmarklet is a javascript: snippet that grabs the current page's URL, title, and selected text, then opens a small save window pointed at your endpoint with those values as parameters. It runs inside arbitrary pages, so keep it tiny and dependency-free, and treat everything it sends as untrusted input to validate server-side.

Authentication can't ride on the bookmarklet living in a page context: embed a long random save token in the generated bookmarklet, scoped to saving only, it can create bookmarks and nothing else, no reads, no deletes. Let the owner rotate the token in settings, which invalidates every previously copied bookmarklet, and show a helpful re-install prompt when a stale token arrives. The save window pre-fills fields, warns about duplicates, and closes on save.

Include a copy-paste install fallback for browsers that block dragging, and a test-save flow confirming the token works.

Done when: saving works from any third-party page in one click, a rotated token cleanly rejects old bookmarklets with a re-install message, and the save token cannot read or modify existing bookmarks.

Frequently asked questions

How long does it take to build your own Raindrop.io?

A basic version — save links, tags, search — takes about 3 hours. Roughly 1 day gets you a solid v1 with bookmarklet, collections, duplicate detection, excerpts. Matching everything Raindrop.io really does (browser extensions, mobile apps, full-page archiving) is closer to 1 month+, which is exactly why you should scope down instead.

How much does Raindrop.io cost if I keep subscribing?

Raindrop.io runs $2.33–$3 per month on public paid plans, which is $28–$36 per year. A focused self-built replacement costs your build time plus close-to-zero hosting.

What stack should I use to build a Raindrop.io alternative?

The build prompt on this page ships in four flavors: the AHA stack (Astro, HTMX, Alpine.js), Next.js, Laravel, and Ruby on Rails. The capability context for this product is Astro, HTMX, D1. Pick the stack you already know — the scope matters more than the framework.

What features does a minimal Raindrop.io replacement need?

A useful v1 needs: one-click saving via a bookmarklet with autofilled title and description; tags, collections, and favorites; full-text search across titles, descriptions, and stored excerpts; card and list views with domain favicons; duplicate detection by normalized URL. Everything else is scope creep until you personally miss it.

What should I deliberately not build?

Do not build team sharing, public collections, AI summaries, or a full read-later reading experience.

Does this build also replace Pinboard and GoodLinks?

Yes. Raindrop.io, Pinboard and GoodLinks all solve the same core job — save links with tags and collections in one place and actually find them again. The scoped v1 on this page covers what most people use any of them for, so one focused build replaces whichever you currently pay for.
