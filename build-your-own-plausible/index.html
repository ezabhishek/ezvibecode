How to Vibe Code Your Own Plausible Alternative

The five website numbers you look at, minus twelve menus. Plausible charges $9–$19 per month — that’s $108–$228 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 8 hoursLovely focused build

Who this replacement is for

This build targets a site owner wanting simple first-party traffic analytics. The goal: show trustworthy aggregate traffic and conversion trends with no visitor profiles. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

Same build, different logo: this v1 also replaces Fathom Analytics, Simple Analytics, Umami and Matomo — they all solve the same core job.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of Plausible you actually use.

EstimateWhat you get
8 hourspageview script, visitor counts, top pages
3 daysgoals, referrers, geo, device breakdown, csv export
1 month+billions-of-events ingestion, funnels, imports, saas hardening — the part you should probably skip

What a minimal Plausible alternative needs

  • tiny pageview and custom-event script
  • dashboard for visitors, views, bounce proxy, and visit duration
  • top pages, referrers, countries, and device classes
  • goal definitions with conversion rate
  • date comparison and CSV export

Data model

Site, PageView, CustomEvent, Goal

Integrations

first-party script endpoint, GeoIP country lookup

Capability context

Workers, Analytics Engine, Astro

The guardrail

Do not set tracking cookies or store full IP addresses, user agents, or persistent identifiers.

Deliberate non-goals

Do not build attribution modeling, ad integrations, user journeys, or raw event replay.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Plainstats”, a deliberately focused alternative to Plausible. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: a site owner wanting simple first-party traffic analytics.
Primary outcome: show trustworthy aggregate traffic and conversion trends with no visitor profiles.
Product principle: optimize the exact workflow below instead of copying the full breadth of Plausible. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The owner adds a site, copies the first-party tracking snippet, restricts accepted origins, visits the site, and confirms the first pageview in installation diagnostics.
2. A visitor navigates several pages and completes a named custom event; edge collection updates aggregate visit, duration, page, referrer, country, device, and goal metrics without cookies.
3. The owner compares this month with the previous period, drills from a traffic change into pages and referrers, inspects goal conversion rates, and exports the filtered aggregates.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Sites and setup: site list, live or waiting state, snippet, allowed domains, timezone, installation test, and recent rejected-event diagnostics.
2. Overview dashboard: visitors, views, bounce proxy, visit duration, comparison deltas, daily trend, realtime indicator, and metric definitions.
3. Breakdowns: top pages, entry pages, referrer domains, countries, browsers, operating systems, and device classes with cross-filtering and pagination.
4. Goals and export: page or custom-event goal definitions, conversions and rates over time, goal breakdowns, date comparison, and aggregate CSV download.

CORE CAPABILITIES
1. tiny pageview and custom-event script
2. dashboard for visitors, views, bounce proxy, and visit duration
3. top pages, referrers, countries, and device classes
4. goal definitions with conversion rate
5. date comparison and CSV export

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Set no tracking cookies and persist no full IP address, raw user agent, or cross-day visitor identifier; derive any daily uniqueness key transiently with a rotating secret.
2. Accept events only for configured origins and site identifiers, normalize paths without sensitive query values, validate custom-event names, and rate-limit abusive clients.
3. Define visitors, bounce proxy, duration, and conversion rate once in code and apply the same timezone-aware formulas to cards, charts, comparisons, and exports.
4. Aggregate accepted events asynchronously with idempotent event identifiers so retries do not inflate counts, while late events update the correct site-local day.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Site, PageView, CustomEvent, Goal. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Workers, Analytics Engine, Astro as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with first-party script endpoint and GeoIP country lookup. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Do not set tracking cookies or store full IP addresses, user agents, or persistent identifiers.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. Given one visitor viewing three pages on the same site-local day, the dashboard shows three views and one approximate visitor without storing a reusable visitor profile.
2. Given a custom event matching an active goal, the event increments that goal once and its conversion rate uses the same filtered visitor denominator as the dashboard.
3. Given an event from an unapproved origin or with a malformed site identifier, collection is rejected and no analytics aggregate changes.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not build attribution modeling, ad integrations, user journeys, or raw event replay.

Not ready to replace all of Plausible? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

Counting visitors you can’t recognize tomorrowA rotating daily salt turns unique-visitor counting into deliberate amnesia.
Build cookieless unique-visitor counting for a web analytics service.

No cookies, no localStorage, no persistent identifiers. Instead, derive a transient daily key: hash(site id, IP address, user agent, daily rotating salt). Use it only to decide "have we seen this visitor today" — increment the visitor count on first sight, only the pageview count afterwards. The salt rotates every day (in the site's timezone) and old salts are destroyed, which makes cross-day correlation cryptographically impossible rather than just promised. The raw IP is used as hash input and then discarded; it never touches disk.

Get the details right: the hash lives in a fast store with a 24-plus-hour TTL, keys expire on their own, and the same visitor viewing three pages on one site-local day counts as one visitor and three views. A visitor returning tomorrow is a new visitor by design — document this as the honest tradeoff it is.

Done when: three same-day pageviews yield one visitor, the database contains no IPs and no cross-day identifiers, and yesterday's salt cannot regenerate today's keys.
One definition of bounce, everywhereTimezone-aware metric formulas defined once, so cards and CSVs can never disagree.
Build the metrics core for a website analytics dashboard: visitors, views, bounce proxy, visit duration, and conversion rate, each defined exactly once in code.

The trap this prevents: the overview card, the trend chart, the comparison delta, and the CSV export each reimplementing "bounce rate" slightly differently and drifting apart. Put every formula in one module — bounce proxy is single-pageview visits over total visits, duration comes from first-to-last event within a visit window, conversion rate uses the same filtered visitor denominator as the dashboard — and make every surface call it.

Day bucketing is timezone-aware: each site has a configured timezone, and events aggregate into that site-local day. A pageview at 11:30 PM in Rome lands on Tuesday even if it is Wednesday in UTC. Late-arriving events (delayed beacons, retries) update the day they belong to, not the day they arrived.

Support date-range comparison (this month versus last) computed through the same code path, deltas included.

Done when: card, chart, comparison, and export agree to the digit for any range, and a late event lands in its correct site-local day.
The aggregation pipeline that shrugs at retriesIdempotent event IDs so a retried beacon never inflates a count.
Build the ingestion-to-aggregation pipeline for an analytics service, hardened against every kind of duplicate.

The client beacon assigns each event a unique event id at creation. The collector accepts the event, acknowledges fast, and hands it to an async aggregation step — collection must never block on aggregation, and a slow database must not slow the tracked site.

Aggregation is where idempotency lives: before folding an event into its counters (pageviews, visitors, goals, per-dimension breakdowns), check whether that event id was already processed; if so, skip it silently. This makes the whole pipeline safe against client retries (flaky mobile networks resend beacons), collector retries, and queue redeliveries — all three happen in practice.

Keep the processed-id set bounded: ids only need remembering for a dedupe window (say 48 hours), after which they expire. Counters update atomically so concurrent aggregation workers do not lose increments.

Done when: replaying the same event five times changes counters once, a paused aggregator catches up without drift, and collection latency stays flat while aggregation backlogs.
The bouncer at the ingest doorOrigin allowlists, path scrubbing, and rate limits before anything counts.
Build the validation gate for an analytics collection endpoint — everything that happens before an event is allowed to exist.

Check provenance first: the event's site id must exist, and the request's origin must be on that site's configured domain allowlist. Wrong origin or malformed site id means rejection with no aggregate touched — and a rejection counter per site, surfaced in installation diagnostics so owners can debug their setup instead of emailing you.

Scrub paths before storage: strip query strings entirely or keep only an explicit safe-list, because URLs arrive carrying session tokens, reset codes, and email addresses. Normalize trailing slashes and case so /Pricing and /pricing/ are one page. Validate custom event names against a strict pattern (length cap, safe characters) to keep garbage out of dropdowns.

Rate-limit per site and per client aggressively — a broken single-page app in a render loop can emit thousands of events a minute and quietly wreck both your bill and the site's stats.

Done when: unapproved origins change nothing, no stored path contains a query secret, and a synthetic event flood hits the limiter instead of the database.
