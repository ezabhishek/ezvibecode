How to Vibe Code Your Own Zapier Alternative

You need a few reliable workflows, not 7,000 connectors. Zapier charges $30–$69 per month — that’s $360–$828 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 3 daysFor your five automations

Who this replacement is for

This build targets an operations team running a known set of webhook-driven automations. The goal: receive events, transform data, and run a short sequence of dependable actions. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

Same build, different logo: this v1 also replaces n8n and Pipedream — they all solve the same core job.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of Zapier you actually use.

EstimateWhat you get
3 dayswebhook trigger, transform step, http action
2 weeks+linear workflows, run history, retries, secrets, replay
3 months+7,000-connector marketplace, oauth for everything, polling triggers — the part you should probably skip

What a minimal Zapier alternative needs

  • webhook triggers with a copyable endpoint and sample payload
  • linear workflows containing filter, transform, HTTP request, delay, and email steps
  • secret references separated from workflow configuration
  • run history with per-step input, output, duration, and retry
  • manual replay from a failed step and workflow enable or disable

Data model

Workflow, Step, SecretReference, Run, StepRun

Integrations

webhooks, HTTP APIs, email, Queues

Capability context

Workers, Workflows, D1

The guardrail

Redact secrets from logs, sign incoming hooks where possible, and make retries idempotent.

Deliberate non-goals

Do not create a public connector marketplace, branching canvas, arbitrary code execution, or polling triggers.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Whenhook”, a deliberately focused alternative to Zapier. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: an operations team running a known set of webhook-driven automations.
Primary outcome: receive events, transform data, and run a short sequence of dependable actions.
Product principle: optimize the exact workflow below instead of copying the full breadth of Zapier. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. An operator creates a workflow, receives a webhook URL, captures a sample event, adds filter, transform, HTTP request, and email steps, tests it, then enables a published revision.
2. A signed webhook starts a run, each step consumes the previous output, a delay resumes durably, and the run detail shows redacted inputs, outputs, durations, and final status.
3. An HTTP action fails after retryable errors; the operator fixes its credential, replays from the failed step, and completes the run without repeating earlier successful side effects.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Workflow list: enabled state, trigger URL, published revision, last run, recent success rate, current failures, duplicate, disable, and create actions.
2. Linear workflow editor: ordered step list, trigger settings, filter and transform configuration, secret references, step test, reorder controls, validation, and publish action.
3. Webhook and test console: copyable endpoint, signing-secret status, captured sample payloads, headers, schema preview, test event, and payload-size errors.
4. Run detail: run status and timeline, per-step attempt count, redacted input and output, duration, error category, logs, replay-from-failure, and cancel controls.

CORE CAPABILITIES
1. webhook triggers with a copyable endpoint and sample payload
2. linear workflows containing filter, transform, HTTP request, delay, and email steps
3. secret references separated from workflow configuration
4. run history with per-step input, output, duration, and retry
5. manual replay from a failed step and workflow enable or disable

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Enabled executions use an immutable published workflow revision; edits remain a draft until validation succeeds and the operator explicitly republishes.
2. Limit webhook body and header sizes, verify configured signatures before enqueueing, reject stale replayed deliveries, and deduplicate events using a provider or generated event key.
3. Resolve field expressions only from the trigger and prior step outputs, validate missing paths and types, and keep filters and transforms deterministic.
4. Persist step completion before advancing, redact credential values everywhere, and require stable idempotency keys for retryable HTTP, email, and manual replay side effects.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Workflow, Step, SecretReference, Run, StepRun. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Workers, Workflows, D1 as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with webhooks and HTTP APIs and email and Queues. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Redact secrets from logs, sign incoming hooks where possible, and make retries idempotent.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. Given an invalid webhook signature, the request is rejected, no run is created, and no portion of the submitted secret or payload appears in logs.
2. Given an event that fails a filter, the run completes as filtered with later actions skipped rather than marked failed.
3. Given a destination timeout after earlier steps succeeded, replaying from the failed step reuses the saved prior output and does not resend an earlier email.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not create a public connector marketplace, branching canvas, arbitrary code execution, or polling triggers.

Build just one piece

Not ready to replace all of Zapier? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

The webhook door with a bouncerSignature checks, staleness windows, and event dedupe before anything runs.
Build the inbound webhook receiver for a workflow automation tool — the gate every event passes before a run may start.

Verify the configured signature scheme (HMAC over the raw body is the common case) using constant-time comparison, on the exact bytes received — parse-then-reverify is how signatures break. Enforce a staleness window using the timestamp in the signed material, so a captured request replayed an hour later is rejected. Cap body and header sizes before reading the full payload.

Deduplicate events: prefer the provider's event id when one exists, otherwise derive a key from a hash of the signed content plus timestamp. A duplicate key acknowledges success but starts no second run — providers retry on slow responses, so acknowledge fast and hand off to the run queue asynchronously.

On any rejection, log the reason category only: no payload bytes, no header values, no fragment of the secret. Rejected traffic is exactly the traffic you must not archive.

Done when: a tampered body is rejected in constant time, a replayed capture is refused as stale, a retried delivery starts exactly one run, and rejection logs contain zero payload content.
Replay from step four without re-firing step twoPersisted per-step outputs make retries surgical instead of shotgun.
Build replay-from-failure for a linear workflow runner: when step four dies, fix the cause and resume from step four — with steps one through three never re-executing.

The foundation is persistence: after each step completes, durably record its output and status before advancing. A run is a chain of checkpoints, not one in-memory pass. When the operator replays from the failed step, load the saved outputs of all prior steps and feed them in as if the run had never stopped — the step-two email that already went out must not send again, and the step-three HTTP call must not repeat.

The replayed step itself needs idempotency for the murky case where it failed after side effects (a timeout following a successful downstream write): each side-effecting step carries a stable idempotency key per (run, step) so the destination can dedupe.

Record replay lineage — attempt count and timestamps per step — and mark the run's final status from the latest attempt. Bound automatic retries; replay past the cap is a human decision.

Done when: replaying a failed step reuses saved prior outputs byte-for-byte, earlier side effects never repeat, and the run history shows every attempt.
Editing a workflow that’s currently runningImmutable published revisions; drafts don’t exist until validation says so.
Build revision management for a workflow automation tool, so editing never mutates what is executing.

Publishing snapshots the workflow — steps, order, configuration, secret references — into an immutable revision. The trigger endpoint always executes the currently published revision. Edits accumulate in a draft that has zero runtime effect until the operator republishes; a half-edited draft can never be what a webhook fires into. Publishing validates first: complete step configs, resolvable secret references, field expressions referencing only steps that exist earlier — and refuses with pointed errors otherwise.

The concurrency rule: a run pins its revision at start and finishes on it, even if a new revision is published mid-run. Two runs from different revisions may execute simultaneously; each run's history records which revision it used, so debugging an old failure shows the workflow as it was then, not as it is now.

Disabling a workflow stops new runs immediately while letting in-flight runs finish.

Done when: publishing mid-run changes nothing for that run, a draft with a broken expression cannot be published, and every historical run displays its own revision.
The dot-path resolver that fails loudlyDeterministic field expressions from trigger and prior outputs, with typed errors.
Build the field-expression resolver for a workflow tool: the mechanism by which step four says "use the email from the trigger and the id from step two's response."

Expressions are dot-paths with array indices (trigger.body.customer.email, steps.http1.response.items.0.id) resolvable only against the trigger payload and outputs of earlier steps — forward references fail validation at publish time. At runtime, resolution is strict and typed: a missing path produces a clear error naming the path and the step that needed it, not undefined silently interpolated into an HTTP body. Distinguish missing from legitimately null, because upstream APIs mean different things by each.

Keep evaluation deterministic: no clock access, no randomness, no network — the same inputs must resolve identically on replay, or replay-from-failure produces different requests than the original run.

Filters use the same resolver with comparison operators. A filter evaluating false ends the run as filtered — a successful completion state where later steps are skipped — never as failed. Alerting that pages someone because a filter did its job is a design bug.

Done when: a missing path fails with the exact path named, replays resolve identically, and filtered runs show as filtered rather than failed.

Frequently asked questions

How long does it take to build your own Zapier?

A basic version — webhook trigger, transform step, http action — takes about 3 days. Roughly 2 weeks+ gets you a solid v1 with linear workflows, run history, retries, secrets, replay. Matching everything Zapier really does (7,000-connector marketplace, oauth for everything, polling triggers) is closer to 3 months+, which is exactly why you should scope down instead.

How much does Zapier cost if I keep subscribing?

Zapier runs $30–$69 per month on public paid plans, which is $360–$828 per year. A focused self-built replacement costs your build time plus close-to-zero hosting.

What stack should I use to build a Zapier alternative?

The build prompt on this page ships in four flavors: the AHA stack (Astro, HTMX, Alpine.js), Next.js, Laravel, and Ruby on Rails. The capability context for this product is Workers, Workflows, D1. Pick the stack you already know — the scope matters more than the framework.

What features does a minimal Zapier replacement need?

A useful v1 needs: webhook triggers with a copyable endpoint and sample payload; linear workflows containing filter, transform, HTTP request, delay, and email steps; secret references separated from workflow configuration; run history with per-step input, output, duration, and retry; manual replay from a failed step and workflow enable or disable. Everything else is scope creep until you personally miss it.

What should I deliberately not build?

Do not create a public connector marketplace, branching canvas, arbitrary code execution, or polling triggers.

Does this build also replace n8n and Pipedream?

Yes. Zapier, n8n and Pipedream all solve the same core job — receive events, transform data, and run a short sequence of dependable actions. The scoped v1 on this page covers what most people use any of them for, so one focused build replaces whichever you currently pay for.
