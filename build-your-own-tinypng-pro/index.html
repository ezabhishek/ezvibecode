How to Vibe Code Your Own TinyPNG Pro Alternative

Drop image. Make image smaller. Fin. TinyPNG Pro charges $25–$39 per month — that’s $300–$468 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 60 minEmbarrassingly easy

Who this replacement is for

This build targets a designer compressing batches of web images. The goal: compress common image formats locally and make the savings obvious. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of TinyPNG Pro you actually use.

EstimateWhat you get
60 mindrop images, compress, download
3 hoursquality controls, side-by-side preview, zip export
1 weekpublic api, cdn delivery, cms plugins, accounts — the part you should probably skip

What a minimal TinyPNG Pro alternative needs

  • drag-and-drop or file picker for multiple images
  • quality controls with sensible per-format defaults
  • before and after dimensions, bytes, and percentage saved
  • side-by-side preview for the selected image
  • download one file or all results as a ZIP

Data model

local ProcessingJob and ImageResult objects only

Integrations

browser Canvas and WebCodecs when supported

Capability context

Astro, Alpine, Browser API

The guardrail

Process images in the browser by default so originals never leave the device.

Deliberate non-goals

Do not add accounts, cloud storage, billing, or an image CDN.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Squooshbox”, a deliberately focused alternative to TinyPNG Pro. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: a designer compressing batches of web images.
Primary outcome: compress common image formats locally and make the savings obvious.
Product principle: optimize the exact workflow below instead of copying the full breadth of TinyPNG Pro. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The user drops a mixed batch of images, watches each file validate and compress locally, then compares original and result sizes.
2. The user selects one image, adjusts output format and quality, examines a split preview, and applies those settings to selected files.
3. The user downloads one optimized image or a ZIP with predictable names, while unsupported and failed files remain clearly identified.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Workspace: prominent drop zone, file picker, privacy statement, batch list, overall bytes saved, clear-all, and download-all controls.
2. Image row: thumbnail, source and output format, dimensions, original bytes, result bytes, savings percentage, state, and remove action.
3. Inspector: zoomable before-and-after split view, format, quality, resize controls, metadata policy, and live recompression indicator.
4. Completion state: summary by success and failure, ZIP size, filenames, and a reminder that refreshing discards all local work.

CORE CAPABILITIES
1. drag-and-drop or file picker for multiple images
2. quality controls with sensible per-format defaults
3. before and after dimensions, bytes, and percentage saved
4. side-by-side preview for the selected image
5. download one file or all results as a ZIP

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Process files entirely in the browser, revoke object URLs after use, and never send image bytes to analytics or a server.
2. Preserve aspect ratio by default, prevent accidental upscaling, enforce pixel and memory limits, and explain unsupported browser capabilities.
3. Never replace the original file in place; produce a deterministic suffix and resolve duplicate output names inside ZIP downloads.
4. Run a bounded number of compression jobs concurrently so a large batch keeps the interface responsive and can be canceled.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on local ProcessingJob and ImageResult objects only. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Astro, Alpine, Browser API as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with browser Canvas and WebCodecs when supported. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Process images in the browser by default so originals never leave the device.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. A valid JPEG batch finishes without network requests and download-all returns a ZIP containing one result for each successful source.
2. An oversized or unsupported image fails independently with a clear reason while the rest of the batch continues processing.
3. Changing quality updates the selected preview and byte estimate, but does not affect other files until apply-to-selected is confirmed.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not add accounts, cloud storage, billing, or an image CDN.

Build just one piece

Not ready to replace all of TinyPNG Pro? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

Compress 200 images without freezing the tabA worker pool with a queue, a cancel button, and no dead tabs.
Build a bounded-concurrency compression pipeline that keeps a browser tab alive through a 200-image batch.

Decode and encode off the main thread in a pool of web workers. Pick a bound — hardware concurrency minus one, capped — and queue the rest. Each file is an independent job with states: queued, processing, done, failed. One corrupt file fails alone; the batch marches on.

Cancellation is the tricky part: cancelling a queued job just removes it, but cancelling an in-flight job signals the worker and discards its result when it lands — a result arriving after cancellation must not resurrect a removed row. Clear-all cancels everything and actually releases memory: revoke object URLs, close image bitmaps, drop references.

Report progress honestly: per-file state transitions plus an overall count, driven by worker messages, throttled so 200 rapid completions do not jank the interface with re-renders.

Done when: a 200-file batch never freezes scrolling or input, cancelling mid-batch stops future work and leaks nothing, and one poisoned file leaves 199 successes.
A before-and-after slider that tells the truthSame region, same zoom, true pixels — or the comparison is fiction.
Build a before-and-after split preview for image compression that does not lie.

Show original and compressed in one viewport with a draggable divider. Both halves render from the same zoom and pan state — comparing two different regions is worse than useless. Compare at true 1:1 device pixels when zoomed to 100 percent: no CSS scaling, no browser smoothing, because a downscaled preview hides exactly the artifacts you are checking for. Account for devicePixelRatio so 100 percent means one image pixel per physical pixel.

Wire the quality and format controls to a live recompress: debounce slider movement, recompress only the selected image in a worker, and show a busy indicator plus an updated byte estimate. A stale result landing after a newer adjustment gets discarded — last request wins.

Zoom toward the cursor, clamp panning to the image bounds, and add a hold-to-compare toggle that flips the full view between original and result.

Done when: both panes always show the identical region at identical scale, JPEG artifacts are visible at 100 percent exactly as they will be in the saved file, and scrubbing the quality slider never queues a backlog of recompressions.
Build the ZIP yourself, byte by byteLocal headers, central directory, CRC-32 — written by hand, in the tab.
Build in-browser ZIP assembly for a batch of compressed images. No server, no library black box.

Write the format yourself: for each file, a local file header, then the data, then one central directory at the end with matching entries and CRC-32 checksums. Use store mode (method 0, no compression) — the images are already compressed, and zipping them again wastes cycles for nothing. Compute CRC-32 incrementally as results arrive. Reach for ZIP64 extensions only if the totals demand it; otherwise stay classic for maximum extractor compatibility.

Naming needs rules: deterministic output names (photo.jpg becomes photo.min.jpg, or photo.webp on a format change), and duplicate names inside one archive resolve with a numeric suffix, because two different photo.jpg sources must not silently overwrite each other.

Assemble via a stream or a list of Blob parts rather than one giant ArrayBuffer, so a 300 MB batch does not double its memory footprint.

Done when: the archive extracts correctly with macOS Archive Utility, Windows Explorer, and command-line unzip, every successful source has exactly one entry with a valid CRC, and duplicate filenames never collide.
The 80-megapixel photo that must not crash the tabMagic bytes, pixel budgets, and codecs you detect instead of assume.
Build the intake and validation layer for a browser image tool that strangers will feed garbage.

Before decoding anything, check the cheap signals: enforce file size caps, and reject non-images by sniffing magic bytes rather than trusting extensions or MIME types. Read dimensions without a full decode where the format allows, and enforce a pixel budget — an 80-megapixel photo decoded to RGBA is over 300 MB of memory before you have done anything. Refuse or downscale-on-decode past the budget, with an explanation.

Feature-detect encoders honestly: not every browser encodes webp or avif. Probe once at startup and hide unsupported output formats instead of failing at download time. Prevent accidental upscaling: resize controls clamp to source dimensions unless the user explicitly overrides.

Hygiene: revoke every object URL after use, close ImageBitmaps, and turn each decode failure into a per-file error with a reason — corrupt, too large, unsupported — while the rest of the batch continues.

Done when: a crafted 100-megapixel file is rejected with a clear message instead of a crashed tab, renamed .txt files never reach the decoder, and memory stays flat across a long session.

Frequently asked questions

How long does it take to build your own TinyPNG Pro?

A basic version — drop images, compress, download — takes about 60 min. Roughly 3 hours gets you a solid v1 with quality controls, side-by-side preview, zip export. Matching everything TinyPNG Pro really does (public api, cdn delivery, cms plugins, accounts) is closer to 1 week, which is exactly why you should scope down instead.

How much does TinyPNG Pro cost if I keep subscribing?

TinyPNG Pro runs $25–$39 per month on public paid plans, which is $300–$468 per year. A focused self-built replacement costs your build time plus close-to-zero hosting.

What stack should I use to build a TinyPNG Pro alternative?

The build prompt on this page ships in four flavors: the AHA stack (Astro, HTMX, Alpine.js), Next.js, Laravel, and Ruby on Rails. The capability context for this product is Astro, Alpine, Browser API. Pick the stack you already know — the scope matters more than the framework.

What features does a minimal TinyPNG Pro replacement need?

A useful v1 needs: drag-and-drop or file picker for multiple images; quality controls with sensible per-format defaults; before and after dimensions, bytes, and percentage saved; side-by-side preview for the selected image; download one file or all results as a ZIP. Everything else is scope creep until you personally miss it.

What should I deliberately not build?
