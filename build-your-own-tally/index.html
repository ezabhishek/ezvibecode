How to Vibe Code Your Own Tally Alternative

A clean document-like form builder with the exports you need. Tally charges $29–$89 per month — that’s $348–$1068 a year — for something you can replace with focused software of your own. Here is the honest scope, the honest timeline, and the exact prompt to hand your coding agent.

from 8 hoursForms are wonderfully finite

Who this replacement is for

This build targets a small team publishing lead, feedback, and application forms. The goal: compose branded forms quickly, collect dependable responses, and route them to existing tools. If you need more than that, keep paying — the point of building it yourself is owning a tool shaped exactly like your workflow, not re-implementing a venture-funded roadmap.

Same build, different logo: this v1 also replaces Fillout and Paperform — they all solve the same core job.

How long it actually takes

One number would be a lie, so here are three. Each tier is a real, usable product — pick the one that matches how much of Tally you actually use.

EstimateWhat you get
8 hoursblock builder, response table, csv export
3 daysconditional visibility, file uploads, signed webhooks
1 month+payments, quizzes, template gallery, integration marketplace — the part you should probably skip

What a minimal Tally alternative needs

  • document-style builder with text, choice, rating, date, file, and contact blocks
  • required fields, page breaks, hidden fields, and simple conditional visibility
  • custom slug, colors, logo, thank-you state, and close date
  • response table with filters, detail view, and CSV export
  • email notification plus signed outbound webhook

Data model

Form, Block, Option, LogicRule, Submission, Answer

Integrations

transactional email, webhooks, R2 object storage

Capability context

Astro, HTMX, D1

The guardrail

Validate every answer against the published form version, scan and isolate uploads, rate-limit public submissions, and sign webhook deliveries.

Deliberate non-goals

Do not build payments, quizzes, collaborative editing, an integration marketplace, advanced branching, or a public template gallery.

The complete build prompt

Copy this into your coding agent of choice. It is scoped for a useful v1 — journeys, screens, business rules, data model, security, tests, and acceptance scenarios included. Pick your stack:

You are building a production-ready software product named “Formlet”, a deliberately focused alternative to Tally. Build a complete, usable vertical slice—not a landing page, static mockup, or disconnected collection of components.

WORKING AGREEMENT
Before writing implementation code, produce a short technical plan that names the routes or pages, server actions or endpoints, data tables, important state transitions, authorization boundaries, background jobs, and external adapters. Resolve contradictions in favor of the narrow audience and non-goals below. Prefer a small, legible architecture over speculative abstraction, but do not omit persistence, validation, error handling, or tests.

PRODUCT BRIEF
Primary user: a small team publishing lead, feedback, and application forms.
Primary outcome: compose branded forms quickly, collect dependable responses, and route them to existing tools.
Product principle: optimize the exact workflow below instead of copying the full breadth of Tally. A first-time user should understand what to do from the interface itself, without a tour or documentation.

END-TO-END USER JOURNEYS
Implement all of these flows through the real interface and persistent data layer:
1. The owner creates a form from blank, adds contact, choice, rating, file, and page-break blocks, configures one visibility rule, previews it, and publishes a slug.
2. A visitor completes the published form across two pages, uploads a valid file, submits once, sees the thank-you state, and triggers email and webhook delivery.
3. The owner filters responses, opens one submission, downloads its authorized file, exports matching rows to CSV, closes the form, and verifies new submissions are rejected.

SCREENS AND INFORMATION ARCHITECTURE
Build these as coherent responsive views. Each screen must specify its primary action, secondary actions, visible status, validation feedback, empty state, loading or pending state, success confirmation, and recoverable failure state.
1. Forms dashboard: draft, open, closed states, response count, last response, duplicate, archive, create, and open-public-form actions.
2. Builder: ordered blocks, add menu, field properties, required state, visibility rule, page breaks, theme, slug, preview, save state, and publish validation.
3. Public form: branded content, progressive pages, clear labels, inline and summary errors, upload progress, submit pending state, and thank-you state.
4. Responses: filters, table, submission detail, file access, delivery status, CSV export, retention controls, and close-form action.

CORE CAPABILITIES
1. document-style builder with text, choice, rating, date, file, and contact blocks
2. required fields, page breaks, hidden fields, and simple conditional visibility
3. custom slug, colors, logo, thank-you state, and close date
4. response table with filters, detail view, and CSV export
5. email notification plus signed outbound webhook

DETAILED BEHAVIOR AND BUSINESS RULES
Treat these as server-enforced product requirements, not interface suggestions:
1. Publish an immutable numbered form version; validate a submission against that exact version and preserve its field labels for later exports.
2. Allow only acyclic visibility rules over earlier supported fields, evaluate them identically on client and server, and reject hidden-field answers server-side.
3. Validate uploads by decoded type and size, isolate them privately, scan before download, and issue only short-lived submitter-independent authorized URLs.
4. Commit one submission before enqueueing notifications, sign webhook bodies, use delivery idempotency keys, and escape formulas in CSV exports.

DATA MODEL AND LIFECYCLE
Design a small relational schema centered on Form, Block, Option, LogicRule, Submission, Answer. Before implementing it, document:
1. Each table’s purpose, primary key, ownership or tenant boundary, timestamps, status fields, and important attributes.
2. Foreign keys, uniqueness constraints, check constraints, indexes needed by the named screens, and transaction boundaries for multi-record changes.
3. The allowed lifecycle or state transitions, who may trigger each transition, which transitions are terminal or reversible, and what audit history must remain immutable.
4. Archive, retention, and deletion behavior, including what happens to dependent records and external files.
5. Idempotency strategy for submissions, jobs, imports, notifications, webhooks, or retries where applicable.
Use migrations rather than ad-hoc schema creation. Store time instants consistently and retain named timezone context whenever local schedules or dates matter. Never rely on a counter, disabled button, or client-side check to preserve a business invariant.

USERS, AUTHENTICATION, AND PERMISSIONS
Implement only the roles required by the stated audience. Make the ownership and visibility model explicit before coding. Enforce authorization in every server-side query and mutation, including search, exports, attachments, live updates, and guessed URLs—not merely by hiding controls. Use secure session defaults, protect state-changing requests, and provide an understandable signed-out, expired-session, and forbidden state. Seed distinct users when multiple roles are required so permissions can be demonstrated and tested.

INTERACTION AND VISUAL DIRECTION
The product should feel fast, calm, focused, and credible rather than like a generic admin template. Use a clear visual hierarchy, restrained color, readable typography, generous hit targets, and consistent placement for primary actions. Start with server-rendered HTML and progressively enhance only the interactions that benefit from it. The core workflow must remain understandable if enhancement fails.

Start with server-rendered Astro pages and ordinary HTML forms. Use HTMX for form submissions, partial navigation, and server-driven updates, then Alpine.js only for small local browser state. The core workflow must remain understandable if either enhancement layer fails.

Design mobile layouts intentionally instead of simply stacking desktop panels. Support keyboard navigation, visible focus, semantic landmarks, explicit labels, useful page titles, reduced-motion preferences, and screen-reader announcements for asynchronous results. Never use color alone to communicate state. Destructive actions require clear scope and confirmation; safe repeated actions should be idempotent.

TECHNICAL DIRECTION
Build this version with the AHA stack: Astro for routing, layouts, and server-rendered pages; HTMX for interactions that benefit from HTML fragment responses; and Alpine.js for small, local interface state. Prefer Cloudflare D1 for relational persistence, R2 for object storage, Workers for server endpoints and scheduled work, Durable Objects only for coordinated real-time state, and Workflows or Queues for durable background jobs—but only when the product requirements call for them.

Keep domain rules in testable server-side modules instead of route handlers or UI components. Separate persistence, external providers, and background work behind small interfaces without building a framework. Prefer ordinary HTML forms and URLs for durable navigation; use optimistic interaction only when failure can be reconciled clearly.

The product brief currently identifies Astro, HTMX, D1 as capability context. Preserve any required native, browser-only, edge, storage, real-time, or background-processing capability through a narrow adapter appropriate to the selected framework. If the core workflow genuinely requires native or browser APIs, keep that runtime as the primary execution surface rather than simulating inaccessible capabilities or inventing an unnecessary web surface.

Integrate with transactional email and webhooks and R2 object storage. For every integration:
- List required environment variables in an .env.example without real secrets.
- Add a small adapter with timeouts, normalized errors, and a deterministic local fake or development path.
- Verify inbound signatures and deduplicate provider events where supported.
- Keep credentials server-side, encrypt long-lived provider tokens at rest, and redact secrets and sensitive payloads from logs.
- Define retry, backoff, and idempotency behavior for any side effect that can be repeated.

SECURITY AND PRIVACY
Validate every answer against the published form version, scan and isolate uploads, rate-limit public submissions, and sign webhook deliveries.
Validate, normalize, and length-limit all untrusted input on the server. Escape rendered content by default, sanitize any intentionally accepted markup, rate-limit public or abuse-prone actions, and use private object storage plus short-lived authorized URLs for sensitive files. Collect the minimum personal data necessary for the named workflow. Document retention and deletion behavior. Add specific protections for the riskier surfaces in this app, such as uploads, redirects, outbound requests, email delivery, OAuth, webhooks, CSV import or export, and real-time connections.

ACCEPTANCE SCENARIOS
Automate these app-specific scenarios at the most appropriate level:
1. Given the public page shows a conditional field, tampering with hidden answers is rejected and valid visible answers are stored once.
2. Given a double-click or retried request, one submission exists and each configured delivery is attempted idempotently.
3. Given the form closes while a visitor is completing it, the final server check rejects submission with a clear closed state and stores no partial response.

TESTING
Add focused unit tests for state transitions, authorization predicates, normalization, date or money calculations, and other risky domain rules. Add integration tests for persistence constraints and each external adapter’s success, timeout, retry, and rejection paths. Add at least one browser-level test for every end-to-end journey above, including one small-screen viewport. Tests must use isolated data and run through a documented single command.

OPERATIONS AND FAILURE RECOVERY
Add structured server logs with request, job, or event correlation IDs but no secrets or unnecessarily sensitive data. Make failures actionable in both the interface and logs. Background work must expose pending, succeeded, failed, and retrying states where relevant; do not silently swallow errors. Include safe database migration and rollback guidance, seed data, backup and restore notes, external-data cleanup behavior, and a basic health or diagnostic path appropriate to the stack.

DELIVERABLES
Ship the working application, migrations, representative seed data, tests, .env.example, and a concise README. The README must cover prerequisites, local setup, environment variables, migrations, seed and test commands, deployment, integration setup, backup and restore, security decisions, and known limitations. Seed data should exercise the happy path plus at least one empty, failed, overdue, expired, archived, or permission-restricted state relevant to the product.

DEFINITION OF DONE
The app is complete when a fresh developer can follow the README, create and migrate the database, run the app, sign in as each relevant role, complete every named journey using real persisted data, refresh without losing state, recover from common failures, and use the core interface on phone and desktop. All acceptance scenarios pass, permission boundaries are covered by tests, and no core screen is left as a placeholder.

NON-GOALS
Do not build payments, quizzes, collaborative editing, an integration marketplace, advanced branching, or a public template gallery.

Build just one piece

Not ready to replace all of Tally? Fine. These are the peculiar sub-problems hiding inside it — the parts that are actually interesting to build. Each one is a standalone prompt, scoped to an evening, no strings attached to the full build.

Publish version 3, validate against version 3Editing a live form must never orphan or corrupt the responses already collected.
Build form versioning for a form builder.

Publishing creates an immutable numbered version: a frozen snapshot of blocks, options, validation rules, and labels. The public page always serves the latest published version and embeds its number; every submission is validated against and stored referencing the exact version it was filled from, not whatever the form looks like now.

This is what keeps history sane: the owner deletes a question, reorders pages, renames a field, republishes, and old responses still render correctly with their original labels, and exports covering both eras group answers by version or align on stable field ids across versions where fields survived. Handle the mid-flight case: a visitor loaded version 2, the owner published version 3, the visitor submits, validate against version 2, which is still immutable and available, and accept.

Done when: a submission started before republish validates against its own version, deleting a field never breaks the rendering or export of old responses, and every stored answer resolves to the exact label text the visitor saw.
The branching logic you can’t tie in a knotAcyclic visibility rules, evaluated identically in the browser and on the server.
Build conditional visibility for a form builder: show this field only when an earlier answer matches a condition.

Constrain rules structurally at authoring time: a rule may only reference fields that appear earlier in the form, which makes cycles impossible by construction, reject any attempt to reference a later or self field. Evaluation must be identical client-side and server-side: write one rule-evaluation function specification, implement it twice, and drive both with the same test vectors, because any divergence becomes either a stuck form or a validation hole.

Server-side, the rules are the security boundary: recompute visibility from the submitted answers and reject any answer for a field that evaluates hidden, a tampered request injecting hidden-field answers must fail. Also define chained behavior: hiding a field clears its answer, and fields whose conditions depend on it re-evaluate in order.

Done when: the builder cannot save a rule referencing a later field, a hand-crafted request answering a hidden field is rejected server-side, and the same answers produce identical visibility in browser and API tests.
One click, one row — even when they click twiceDouble-submits, retries, and forms that close mid-fill all resolve to at most one response.
Build submission handling for a public form that copes with real visitor behavior: double-clicks, browser retries, and back-button resubmits.

Issue each rendered form a one-time submission token. The submit endpoint inserts the response keyed by that token with a unique constraint: the first request wins, any duplicate, second click, network-layer retry, replayed request, hits the constraint and returns the same success response as the original, so the visitor sees thank-you either way and exactly one row exists. Disable the button optimistically on the client, but treat the token as the real guarantee.

Run the closed check at final submission time: if the owner closed the form while the visitor was filling it, reject with a clear closed message and store nothing partial. Same for the close date passing mid-fill. Validate everything server-side against the published version before insert, one atomic accept-or-reject.

Done when: hammering submit produces one stored response and consistent success screens, a replayed request cannot create a second row, and a form closing mid-fill rejects cleanly with no partial data stored.
The webhook the receiver can actually trustSigned bodies, delivery idempotency keys, and retries with backoff that eventually give up.
Build outbound webhook delivery for form submissions.

When a submission commits, enqueue a delivery, never send inline with the request, so a slow receiver can't slow submissions. Sign each delivery: compute an HMAC of the exact body with the form's endpoint secret, send it in a header along with a timestamp header to block replays, and document the verification recipe. Include a delivery idempotency key, stable per submission-and-endpoint, so your retries after ambiguous failures don't make the receiver process an order twice.

Retry failed deliveries with exponential backoff and a cap, say five attempts over a few hours, treating timeouts and 5xx as retryable but 4xx as permanent. Record every attempt with status code and duration, show delivery state per submission in the dashboard, and offer manual redelivery, which reuses the same idempotency key.

Done when: a receiver can verify the signature from the docs alone, retries after timeout carry the identical body and key, and a permanently failing endpoint stops retrying and shows a failed state with attempt history.

How much does Tally cost if I keep subscribing?

Tally runs $29–$89 per month on public paid plans, which is $348–$1068 per year. A focused self-built replacement costs your build time plus close-to-zero hosting.

What stack should I use to build a Tally alternative?

What should I deliberately not build?
